# 后端数据库访问与任务领取优化

日期：2026-10-22。用户要求检查后端是否需要优化，并直接完成有必要的改进。本轮根据源码与隔离数据库测量，处理数据量增长时重复查询的问题；保留原 API、权限、幂等、教师确认和持久恢复协议。

## 问题与改动

| 位置 | 原问题 | 当前实现 |
| --- | --- | --- |
| 答案导入预检/提交 | 每行分别查询一次是否已有来源版本，200 行产生 200 次查重查询 | 先验证作业范围，再以完整四字段组合键一次查询，按输入顺序返回；保持原文、时间和冲突校验 |
| 创建批改批次 | 每份答案依次读取、插入目标、加锁，循环中反复自动 flush 关联行 | 批量读取所需答案字段、批量 `ON CONFLICT DO NOTHING`、统一按答案 ID 顺序锁目标、批量写关联 |
| 导出及单项详情 | 对每个目标重复读取其答案、学生、细则、步骤、复核和调用回执 | 共用批量详情装配，固定版本记录按 ID 只读取一次，关联记录分表批量加载；只确认导出先筛选再读取详情 |
| 批次状态刷新 | 在持有批次锁时，把整批状态和复核版本全部取回 Python 计数 | 保持先锁后读，通过 SQL 按状态分组聚合，只返回实际存在的状态组 |
| Harness 任务领取 | 一次性读取全部候选 ID，积压越大，单次领取占用的内存越多 | 按 `(ready_at, id)` 游标每页最多读取 100 个候选，先释放读取连接，再按原顺序锁根任务和目标 |

任务扫描会继续越过被锁定或仍在等待的候选，直到找到可领取工作或读完本次候选，不把“第一页没领取到”解释为空队列。没有采用 OFFSET，也没有在分页读取期间持有数据库长事务。该改动限制候选读取的内存峰值，不承诺消除积压下的全部扫描成本。

导入仍以四字段元组区分身份，包含冒号、Unicode、换行的输入不会被拼接键混淆。提交仍持有作业锁；不同幂等键的相同来源版本只能复用，不能改写已保存答案。批次创建仍依赖数据库唯一约束跨请求去重，目标加锁顺序一致，重复学生和跨题目答案仍被拒绝。

导出继续在 `REPEATABLE READ` 事务内完成所有计数、详情和保存。并发复核可能使 PostgreSQL 外键检查要求重试整个事务；重试可以返回新快照，但不能把旧计数与新明细混合。返回字段、原始答案、复核历史、供应商回执和快照哈希均保留。具有相同创建时间的模型回执按 ID 稳定排序。

本轮不增加缓存层、消息中间件、依赖或数据库迁移。减少重复查询已有直接收益；是否需要新的连接池参数、索引或分布式队列，应依据部署负载和执行计划继续判断。

## 隔离数据库前后对照

使用同一脚本 `backend/tools/benchmark_backend.py`，在专用 `_test` 数据库中分别创建随机 schema。通过实际 FastAPI 路由运行 20/200 人合成班级的预检、导入、批次创建/复用和待复核导出。计数来自 SQLAlchemy `before_cursor_execute`，包括实际 SELECT/INSERT 等语句，不统计驱动隐式事务或准备语句的协议往返。没有调用模型，也没有使用真实师生数据。

200 人场景结果：

| 操作 | 优化前 SQL 条数 | 优化后 SQL 条数 | 本地单次耗时前 → 后 |
| --- | ---: | ---: | ---: |
| 导入预检 | 204 | 5 | 61.58 → 9.44 ms |
| 提交导入 | 212 | 13 | 105.44 → 55.78 ms |
| 创建批次 | 814 | 18 | 321.03 → 50.36 ms |
| 复用目标创建另一批次 | 814 | 18 | 322.78 → 42.30 ms |
| 导出待复核结果 | 2213 | 22 | 713.46 → 70.50 ms |

20 人场景中，预检 24→5、导入 32→13、创建/复用批次 94→18、导出 233→22。优化后的 SQL 次数在两个规模相同；传输正文、JSON 序列化和存储的数据量仍随人数增长。这是本机单次样本，未做多用户压力测试，不把这些耗时解释为生产延迟或容量保证。

机器记录：`.local/e2e/backend-optimization/baseline.json`、`optimized.json`。可复测命令如下；输出文件必须不存在，以免覆盖历史证据：

```powershell
uv run --frozen python backend/tools/benchmark_backend.py --output .local/e2e/backend-optimization/recheck.json
```

脚本只接受 `_test` 数据库，默认使用 20 和 200 人场景，结束后清理随机 schema。SQL 次数上限另纳入正式测试，后续引入逐行数据库访问会触发回归失败。
