# 后端与 Harness 并发、中断恢复检查

日期：2026-10-23。用户要求继续检查性能和稳定性，发现问题直接修复并测试。本轮围绕数据库锁竞争、领取租约、调用前后中断、执行截止时间和定时恢复进行检查。现有功能和历史回归不足以证明项目已经完善；本轮确实复现了遗漏的运行时边界。

## 已复现的问题与修复

| 问题 | 后果 | 修复 |
| --- | --- | --- |
| 批改 Worker 在刷新批次、等待批次锁之前设置租约 | 等待超过租约长度后，领取返回的租约已经过期，未执行有效工作就消耗重试次数 | 保持目标行锁，在批次刷新结束后按数据库当前时间设置完整执行租约；Harness 接收子任务结果后也重新取时、复核截止时间再领取 |
| Harness 提交调用预留后，未在实际调用前重新验证状态；调用期间只检查状态与 epoch | 已取消、租约过期或 owner 已替换的 Worker 仍可能发起请求或继续等待 | 调用前及等待期间读取最小执行字段，检查自身和根任务状态、epoch、owner、租约、执行截止时间；失效即取消等待，HTTP 期间不持有事务或行锁 |
| 准备上下文或预留预算期间越过执行截止时间 | 仍记录调用并把截止时间误报为模型超时，可能消耗无效预算 | 上下文准备后及派发事务结束前复核数据库时间，过期则回滚派发与预留；调用时间同时受根任务和当前任务的剩余时间限制 |
| 工具在有效期内开始，过期后完成 | 仍提交草稿并进入等待教师状态 | 在工具结果、回执和状态一并提交前检查截止时间，过期则回滚整个步骤，再记录截止失败；持久人工等待已冻结执行时钟，继续按原协议处理 |
| 定时唤醒先取有限候选，再逐个跳过锁住的根任务 | 前面的锁住任务占满候选窗口，后续已经到期的任务持续得不到唤醒 | 在数据库选择候选时先对根任务使用 `SKIP LOCKED`，再取一条；每条独立提交，单次扫描仍有处理上限和唯一唤醒回执 |

工作池 `once` 模式新增了跨轮询边界的检查，现有实现通过，不需要修改该行为。另补充超时清理检查：先取消出站请求，再访问数据库判断超时原因，避免数据库故障延长已超时的请求。

## 验证证据

先运行新增回归，原实现出现 **6 个失败场景**：定时唤醒锁竞争、调用前取消/租约过期/owner 更换、上下文越过截止时间、批改领取长时间等待批次锁。随后单独复现工具过期提交，得到 **1 个失败场景**。报告保留在 `.local/e2e/concurrency-recovery/before.xml` 和 `tool-before.xml`。

新增测试还验证：

- 两个各含 4 个槽位的工作池竞争 12 个任务，存在模型调用重叠，每任务仅一次领取、一个产物，终态不残留租约或在途序号。
- 调用进行中租约过期或 owner 更换，取消原请求；新 Worker 恢复时只追加一个未知调用记录，最终只有一个产物，历史预算不抹去。
- 三个同批到期任务中，前两个根任务持锁，扫描上限为 1 时仍能唤醒第三个；解锁后并发扫描只产生各一个回执。
- 批次锁等待超过真实配置的 5 秒租约后，领取仍获得有效租约，批改一次尝试完成。
- 父任务接收子任务结果后获得完整租约，不额外消耗正常恢复的尝试次数。
- 工具越过截止时间时，草稿与事务内效果回滚，待执行调用得到关闭；正常教师暂停、恢复、子任务汇总和预算兼容性继续回归。

修复后的第一组相关测试 **44 项通过**，扩展并发测试后第二组 **76 项通过**。最终后端全量 **484 项全部通过（308.91 秒）**，较上一轮新增 **13 项**；报告为 `.local/e2e/concurrency-recovery/full.xml`。Ruff 检查、**134 个文件**的格式检查和 Git 差异空白检查通过。测试使用随机 schema，完成后清理测试数据。本轮未修改前端，也未重跑浏览器或真实供应商验收。

uv run --frozen pytest -q --junitxml=.local/e2e/concurrency-recovery/recheck.xml

## 仍需保留的边界

当前结果验证受控竞争和故障恢复，不等同于生产容量或长期运行保障。尚需结合实际部署进行持续负载、真实网络/数据库故障、备份恢复演练和运行监控验收；真实教学质量仍需教师标注评测。前阶段的 SQL 优化测量见 [后端访问优化](BACKEND_OPTIMIZATION_2026-10-22.md)。

取消与外部模型请求无法构成一个数据库原子事务：请求已经被供应商接收时，取消本地等待不能保证供应商停止或不计费。未知调用继续保留预留预算，晚到结果仍由租约和 epoch 阻止回写。数据库中断期间保留持久租约，由后续 Worker 在过期后恢复。

本轮没有提交、推送、部署或迁移业务库。代码仍要求既有迁移 `0012`；业务库保留此前的 `0006`，部署新代码仍需先按既定流程备份和迁移。
