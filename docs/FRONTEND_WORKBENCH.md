## 2. 后端改动与兼容性

`service.py` 补充详情读模型字段：

- 批次详情新增 `created_at`、`rubric_version`、`assignment{id,title,course_id,classroom_id}`、`question{id,question_key,version}`。
- 答案详情新增 `student{id,name,external_id}`、`assignment{...}` 和 `question.question_key`。

字段来自已经通过老师范围检查的批次/单项关联，继续在现有只读快照事务中查询。旧字段保留，不增加路由、表或迁移。新建 JSON 导出会包含这些附加详情；数据库里的旧导出快照保持原内容。

复核 POST 仍返回 `{id, revision, confirmed_score}` 回执，前端再读取详情；没有把回执当作完整答案。即使随后 GET 失败，页面保留已提交的决定和返回修订号。

## 4. 用户验收入口

启动命令见 [前端 README](../frontend/README.md)；后端沿用 [根 README](../README.md)。无本次新增迁移，不需要重建或清理现有数据库。

建议验收顺序：

1. 启动已有 API，前端 `npm ci` 后 `npm run dev`，使用现有开发令牌连接。确认课程/作业筛选、批次分页和待复核数量。
2. 选择包含中文、emoji、CRLF、重复文字的合成答案。引用第二次出现的片段，提交后重新打开，检查引用、等级、理由与版本均保留。
3. 对 Jev 的无引用初评，分别尝试“原文支持”“表达缺失”“人工判断”。原文支持缺少引用应阻止提交；空确认分不展示为零。
4. 在两个浏览器页面中修改同一答案。先保存一处，再提交另一处，检查冲突提示、最新内容对比、保留本地编辑和显式重提。
5. 用浏览器网络工具模拟响应丢失。检查编辑锁定及同一次提交重试；服务器只有一次有效复核。不要通过刷新清除未知操作再提交。
6. 创建两种范围的导出，检查 CSV/JSON；修改成绩后旧下载不变化，新快照记录新修订。待确认列不能借建议分冒充已确认成绩。
7. 选择合成失败项，显式补充有限额度并重试；查看状态和失败原因更新。
8. 执行后端 pytest 与前端 test/typecheck/build，另检查窄屏布局、键盘操作、选区定位与隐藏页面轮询。

以上是交付时列出的验收场景；其中批次打开、复核提交、引用、导出创建与 CSV/JSON 下载已在第 6 节自动验收。并发冲突、网络失联、失败项重试、键盘与拖拽仍需人工或后续自动化；390px 已做无横向溢出冒烟。
