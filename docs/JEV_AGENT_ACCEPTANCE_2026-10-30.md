# Agent Loop 调用 Jev 批改工具：实现与验收

本次验收对象是 **Agent Loop → 教学任务读取 → 批改工具 → Jev 判决 → 数据库检查点与初评 → Agent 收集结果**。日期为 2026-10-30。生产代码使用现有 Harness 和批改 Worker；没有新增依赖、数据库迁移或自动成绩确认。

## 本次补齐的实际链路

此前工具目录只有评分细则、备课、补练等任务；Jev 由独立 Worker 处理，尚无 Agent 可调用的作业批改工具。因此，过去 Harness 任务数与批改项数的并列统计，不能证明 Agent 曾调用 Jev 批改工具。

新增 `homework-grading` 任务与 `POST /v1/grading-agent-runs`。工具全部零参数，目标范围来自教师创建任务时的固定输入，模型不能换学生、换答案、改评分细则或换 Jev 配置。

```mermaid
flowchart LR
    A[固定答案版本、确认细则、Jev配置] --> B[Agent Loop]
    B --> C[read_grading_task]
    C --> D[grade_homework]
    D --> E[事务内创建或复用批改目标]
    E --> F[独立批改 Worker 调用 Jev]
    F --> G[判决检查点、证据步骤、分点评估、建议分数入库]
    G --> H[collect_grading_result]
    H --> I[初评执行报告]
    I --> J[教师逐份复核]
```

- `read_grading_task` 读取固定题目、参考、细则哈希与答案数量；原答案由批改 Worker 读取，控制模型无需接触学生身份或整个答案集合。
- `grade_homework` 复用业务事务、唯一键与版本化 profile，只返回“已提交”回执。批次创建、Agent 状态、工具结果与回执在同一事务中提交。
- 等待批改时释放 Agent 租约，一秒后由运行时重新检查，不调用控制模型，不增加模型/工具计数，不消耗自动重试次数；原任务截止时间仍有效。需要同时运行 Harness Worker 和批改 Worker。
- `collect_grading_result` 只有在批次终结后才能生成报告，核对答案、细则和 profile 范围，分别记录成功、失败、可计分与弃权数量。Agent 的 `completed` 表示报告已收集，是否全部批改成功需读取报告的 `outcome`。
- `completed` 不代表教师确认。通用产物确认接口不能确认这类执行报告，成绩仍走逐项复核入口。Jev 证据策略仍是 `manual-evidence-v1`：保存证据步骤与答案绑定，但原文证据须教师选取。
- Agent 被取消或超时后，已经提交的批改批次仍是独立、可追溯的任务；这次没有实现跨两类 Worker 的级联取消。不存在无限重试或取消后自动重提整批的行为。

核心实现：[`harness/grading.py`](../backend/src/teaching_assistant/harness/grading.py)。API、任务目录、模型注册和共享运行时只增加该任务需要的接入点；已有 profile 继续可恢复。

## 验收指标的口径

| 指标 | 分子 / 分母或计算方式 | 用途 |
| --- | --- | --- |
| 完整链路成功率 | 初评成功且所属 Agent 已收集报告的答案数 / 全部提交答案数 | 验证 Agent 工具链，不把提交回执当完成 |
| 按时完成率 | 在预设时限内初评成功并完成报告收集的答案数 / 全部提交答案数 | 包含控制模型和队列等待 |
| 初评流程完成率 | `succeeded` 答案数 / 全部提交答案数 | 弃权可完成流程，但没有可用分数 |
| 可计分覆盖率 | 成功且建议总分非空的答案数 / 全部提交答案数 | 不将弃权算零分，不把失败从分母删除 |
| 入库一致性 | 全量核对答案哈希、固定版本、评分点与分值、总分重算、检查点回执、预算和唯一记录 | 任一不一致即工程验收失败 |
| 延迟 | 初评项创建到成功事务时间；Agent 创建到报告收集时间；首领等待时间；Jev 请求耗时 | 分别报告 P50/P95/P99/最大值；失败不会出现在成功延迟样本中，须同时看失败率 |
| 等级正确率 | 与教师标签一致的评分点数 / 有预测且有标签的评分点数 | 必须同时报告覆盖率 |
| 端到端正确率 | 与教师标签一致的评分点数 / 全部应评、已标注评分点数 | 失败、漏评、弃权保留在分母 |
| 总分 MAE | 完整预测总分与教师总分的绝对差均值 | 明确可计算的完整答案数，不能只报 MAE |
| 重试与成本 | HTTP 请求尝试、未知调用、usage 缺失、控制模型次数 | 未知调用不退还预算；无单价时费用为 null |

基准脚本默认示例门槛：完整链路及按时完成率 ≥99%，可计分覆盖率 ≥95%，时限 60 秒。参数可覆盖；本轮负载测试在开始前统一指定 120 秒。这些是实验门槛，**不是行业认证标准或生产 SLA**。故障模式按预期的恢复/拒绝结果验收，另报业务 SLO 是否通过，不能把故障处理通过说成 100% 批改成功。

Jev 的 `confidence` 是由返回概率分布计算的统计量，不能直接充当本项目的实际评分正确率；正确性必须与外部教师标签对照。[TypeSafe 官方说明](https://docs.typesafe.ai/confidence)

## 可复现基准

入口：[`benchmark_jev_agent.py`](../backend/tools/benchmark_jev_agent.py)。默认使用确定性的控制模型和 Jev HTTP 协议桩，但工具注册、Jev 响应解析、任务领取、重试、事务、检查点和数据库均走实际实现。`--mode live` 才会调用真实 Jev；`--controller deepseek` 才会让真实生成模型选择工具。

要求 `TA_TEST_DATABASE_URL` 为 `postgresql+asyncpg`、库名以 `_test` 结尾。每次创建随机 `jev_benchmark_<uuid>` schema，应用真实迁移，最后删除本次 schema；不迁移业务库。输出目录必须不存在，原始报告不会被覆盖。测试结束后库内合成记录被清理，JSON 保存聚合审计结果、配置、数据集哈希和已测运行的版本信息。

```powershell
# 默认只使用协议模拟，无付费请求：4 个任务，每个 50 份答案，4 个批改槽。
uv run --frozen python backend/tools/benchmark_jev_agent.py --runs 4 --answers 50 --workers 4 --deadline 300 --slo-seconds 120 --max-provider-calls 1000 --output .local/e2e/jev-agent/recheck-load

# 混合故障：每八份包含一次 429、503、非法响应、并列弃权、401、超时，以及两个正常样本。
uv run --frozen python backend/tools/benchmark_jev_agent.py --runs 4 --answers 50 --workers 8 --faults --deadline 300 --slo-seconds 120 --max-provider-calls 1000 --output .local/e2e/jev-agent/recheck-fault

# 显式真实模型调用；使用项目自带的四份合成样例，不构成教师质量评测。
uv run --frozen python backend/tools/benchmark_jev_agent.py --mode live --controller deepseek --runs 1 --answers 4 --workers 2 --deadline 180 --slo-seconds 120 --max-provider-calls 12 --output .local/e2e/jev-agent/recheck-live

# 专项回归，必须配置专用测试库，不能将数据库测试 skipped 当作通过。
uv run --frozen pytest -q backend/tests/test_harness_grading.py backend/tests/test_jev_benchmark_metrics.py
```

`--workers N` 表示单个进程中的 N 个 Harness 实例加 N 个批改 Worker 实例，不能写成 N 个独立进程。负载方式是预先提交固定批次再排空，不是固定到达率测试；API 使用进程内 ASGI，不包含网关、TLS 或 HTTP 入口容量。固定到达率的生产压力应独立于响应时间发起，避免系统变慢时负载发生器自动减速而低估排队。[k6 官方说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)

真实模式最多接受 200 份答案、1000 次 Jev 请求上限；每个 Agent 默认最多 6 次控制模型调用。本轮显式缩至 4 份答案、12 次 Jev 上限。请求发出前扣减共享上限，超时/未知结果不退款。它是单进程基准的请求次数闸门，不是生产环境跨进程的 Jev 费用闸门。教师标签不会传入 Jev；真实模式只发送题目、参考、评分规则和答案正文。

任务参数 `max_model_calls`、`max_total_tokens`、`max_cost_usd` 约束 Harness 控制模型，不能当成 Jev 整批费用上限。Jev 批改保留每份答案的尝试/调用次数限制，基准另设 `--max-provider-calls`；跨进程统一的 Jev 金额预算是后续上线验收项。程序不推测缺失单价，不把未知费用写成零。

## 本轮实测记录

真实小样本报告：`.local/e2e/jev-agent/live-1/report.json`。1 个 Agent，4 份答案，8 次真实 Jev 判决请求、3 次真实 DeepSeek 控制调用，全部完成；8 条分点评估与 16 个持久检查点通过全量审计。Agent 从创建到收集报告约 13.15 秒，初评项最大延迟约 8.92 秒；这是功能冒烟观测，不是生产延迟承诺。

四份样例覆盖完整回答、部分回答、空白答案和答案中的越权指令。8 个评分点与**合成标签**全部一致，总分差为零。报告 `semantic_quality` 为 null，不能对外写成“真实作业准确率 100%”。重复这些样例只增加负载数量，不增加独立质量样本数。

负载和故障原始报告分别保存在 `.local/e2e/jev-agent/load-1/`、`load-4/`、`load-8/`、`load-1000/`、`fault-200/`，各目录含 `report.json`。同机顺序运行，没有同时执行其他数据库测试；150 ms 协议模拟、两个评分点、全部答案先提交再排空。

1000 份负载中，10 个 Agent 全部收集结果，2000 条分点评估、4000 个检查点无缺失，调用计数一致，无重试及残留租约。按初评项入库时间算，120 秒完成率是 76.2%；把 Agent 收集结果也纳入终点则为 70%，二者不能混用。所有初评仍待教师复核。脚本按原定门槛返回非零退出码，未放宽门槛后重跑制造“通过”结论。

4 槽增加到 8 槽没有改善本机吞吐；1000 份的首次领取等待 P95 为 146.07 秒，接近其初评端到端 P95 147.19 秒。排队占主要时间，说明容量约束需要继续定位。当前证据不足以确定是连接池、事务锁、Python 调度还是多者共同作用；下一步应采集锁等待/查询/事件循环指标，再决定优化点。不能由这些单次实验宣称线性扩容或生产最大容量。

200 份混合故障在 37.51 秒内结束，全部 4 个 Agent 收集了真实终态：100 份在 429、503、非法响应或超时后恢复；25 份 401 按不可重试错误失败；25 份并列分布弃权；其余 50 份正常。最终流程成功 175/200，可计分 150/200，350 条分点评估与 700 个检查点通过审计。475 次 Jev 协议请求中，25 次超时保留 `unknown`，没有从次数预算中扣除。故障预期验收通过，业务 SLO 明确为失败。

运行环境：Windows、Python 3.13.5、20 个逻辑 CPU，PostgreSQL 临时实例、默认数据库连接池；后期报告还记录 asyncpg 0.32.0、SQLAlchemy 2.0.55、httpx 0.28.1、pydantic 2.14.1 和生产源文件指纹。没有 HTTP 网关、多个服务进程或真实供应商吞吐压测。真实 Jev 小样本的运行与相关回归有时间重叠，仅用作功能验证；表中负载运行与回归分开进行。

最终全量后端回归 **539 passed，479.40 秒，无失败或跳过**，较既有 521 项新增 18 项；报告为 `.local/e2e/jev-agent/full-tests.xml`。新增测试覆盖完整工具链、恢复等待不消耗模型/尝试预算、限流/超时/非法响应恢复、认证失败、弃权、重复任务复用、权限、超时、工具事务回滚、请求次数上限和准确率分母。Ruff 全后端检查及 **154 个文件**格式检查通过。未改动或重测前端，没有提交、推送、部署或迁移业务库；本轮随机 schema 全部清理，临时数据库实例在验证后停止，复测前需准备可用的专用测试数据库。

## 企业级验收还需哪些证据

本轮提供了完整工具链、真实 Jev 可达性和入库正确性的验证手段；企业级上线验收还应按实际业务量补齐以下独立证据：

1. **教师金标准。** 建议首轮 500–1000 份不同的匿名答案，覆盖不同题目、难度、正确/部分/错误/空白/越权文本。两位教师独立评分，分歧仲裁，记录一致性。开发/阈值选择与 holdout 分离，固定题目、细则、提示与 Jev 版本；按题型和评分点报告覆盖率、准确率、严重误差及总分 MAE。每个数据文件保持现有单题/单细则契约，最多 200 份，可分文件评测。不能把同一答案复制 1000 次当 1000 个独立质量样本。
2. **实际到达率与持续负载。** 按班级数、每班人数、评分点数、供应商配额确定目标；阶梯增压到出现积压，测试突发提交和至少数小时持续运行，观察队列最老任务、数据库连接/锁、CPU/RSS、重试放大和费用。报告能在目标时限内完成的容量，单独测网关与真实 HTTP 服务。
3. **新链路的进程与提交故障。** 在批改工具事务提交前后、Jev 请求进行中、模型响应后入库前、结果收集时强杀独立进程；注入数据库断连，检查已提交结果不丢失、唯一结果不重复、未知外部调用仍计费/占额度。既有 [多进程恢复记录](RUNTIME_STRESS_2026-10-23.md) 可复用其方法，但此前混合负载没有经过本次新批改工具，不能直接当作新链路已通过的证据。
4. **生产运维与权限。** 多教师越权、恶意工具参数和未注册工具；多副本共享 Jev 配额/费用限制；监控、告警、备份恢复与发布回滚。已有开发身份入口不等于正式组织权限体系。

用教师可观察的完整任务结果设 SLO，并持续记录目标与实际差异，比单独报告 HTTP 成功响应数更适合这种异步作业流水线。[Google SRE 的 SLO 方法](https://sre.google/workbook/implementing-slos/)
