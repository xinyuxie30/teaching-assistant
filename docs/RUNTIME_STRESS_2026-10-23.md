# 多进程持续负载与故障恢复演练

日期：2026-10-23。承接 [并发恢复检查](CONCURRENCY_RECOVERY_2026-10-23.md)，本轮使用独立 Worker 进程、真实 PostgreSQL 和 TCP 连接故障，检查强杀与数据库断连后的接管。所有教学数据和模型回复均为合成数据。

## 发现与修复

### 数据库不可用时的重连与日志放大

短时预演暴露两个问题：Harness 工作池会让每个空闲槽位分别尝试失败的领取；批改 Worker 按正常轮询间隔重试，并重复输出完整异常栈。现在同一池首次领取失败后结束本轮领取，对连续失败采用有上限的退避；单 Worker 入口同样处理。最短间隔 250 ms，连续失败逐步增至 2 秒；较慢的配置轮询间隔继续保留，成功后重置。故障等待不增加任务尝试次数，也不退还未知调用预算。

批改错误日志改为事件名和异常类型，避免反复展开异常中的 SQL 参数或模型数据。取消仍及时退出，单次与排空模式仍将错误交给调用者。

同一组 30 秒参数各执行一次：2 个 Harness 进程，每个 2 槽，3 个批改进程，每秒 1 个根任务，两次各 2 秒断连。

| 观测 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 断连期间新连接尝试被拒绝 | 259 | 39 |
| Worker 日志字节数 | 771034 | 2002 |
| 日志行数 | 12326 | 42 |
| 异常栈次数 | 114 | 0 |
| 最终 Harness 任务 / 批改项 | 63 / 21 | 63 / 21 |
| 全量状态、回执、预算和产物审计 | 通过 | 通过 |

这是同参数单次观测，故障命中步骤和调度时序存在差异，不是统计基准。退避会增加恢复等待：修复后短时预演中根任务完成时间 P95 为 6.492 秒、最大 12.014 秒。原始报告在 `.local/e2e/runtime-stress/pilot-1/` 与 `pilot-2/`，日志对照在 `backoff-comparison.json`。

### 嵌套子 Agent 没有恢复调用余量

首次较高负载演练在强杀 Harness 后失败，错误为 `agent_model_budget_exhausted`。确定性回归进一步复现：练习设计协调子任务正常需要三次模型调用，旧子任务上限也是三次；只要有一次已派发但未收到回执的调用，保守记账后就没有完成任务的余量。

新建任务的子任务配置上限改为五次，容纳既有三次尝试上限中的两次恢复。根任务总调用数、token 和费用上限仍然约束整棵树，未知调用仍占预算，实际调用数没有归零或隐去。测试验证一次、两次未知调用后整树分别计 11、12 次，仍在原定 12 次内完成。

这是新配置的指纹变化，保留原 v5 配置以及 v1–v4 恢复支持。子任务选择同时匹配父任务的运行时和调度配置；旧 v5 树仍用三次子任务预算，不能通过重启偷偷增加已冻结的额度。已有任务若确实耗尽预算，仍按原协议停止。

失败证据为 `.local/e2e/runtime-stress/sustained-1/report.json` 和 `child-budget-before.xml`；修复后相关回归为 `child-budget-final.xml`，33 项通过。

### 故障积压放大无效父任务锁竞争

第二轮 5 分钟演练发现另一处缺陷：断连积压产生较多等待父任务后，领取逻辑反复锁住这些尚未得到子结果的父任务。到 303 秒时有 423 个排队任务、128 个等待父任务，却只有 2 个任务在运行；第二次断连后的恢复超过脚本的 60 秒检查窗口。过程中的回执未被清除，错误属于调度进展不足。

候选查询现在用数据库关联条件跳过“首个待接收子结果仍在执行”的父任务，后台显式 join 使用其持久绑定定位对应子任务。它不会等待无关后台子任务；缺失依赖、终态子任务和过期任务仍进入原有加锁检查。真正领取及接收结果继续先锁根任务，再检查状态、权限、期限和回执。

新增回归在串行、并行和后台等待三种模式下均先失败，修复后确认领取子任务前不再对等待父任务进行无效加锁，并验证过期清理仍能触发。相关 43 项回归通过，包括候选分页、后台等待、按顺序汇总、多层预算及旧配置。失败负载记录为 `.local/e2e/runtime-stress/sustained-2/report.json`，前后回归为 `waiting-parent-before.xml`、`waiting-parent-after.xml`。

### 多槽启动时重复构建配置

5 分钟负载通过后的首次全量回归为 502 通过、1 失败；失败点是两个四槽池在原定 2 秒内未建立四路模型调用重叠。测量发现八个槽位逐个生成相同配置目录，仅构造阶段就耗时约 1.47 秒。配置兼容项增加后，这部分同步 CPU 工作影响初始领取和同进程中的其他协程。

现在每个池只生成一次配置目录，之后深拷贝给各槽位，仍使用独立租约 owner、配置快照和执行状态。新增测试先确认发生八次重复构建；修复验证要求仅构建一次，并检查一个槽位的嵌套配置修改不会影响其他槽位。原有 2 秒就绪限制保持不变。首次全量报告为 `full.xml`，启动优化前后报告为 `pool-startup-before.xml`、`pool-startup-after.xml`。

## 演练方法与复测

入口为 `backend/tools/verify_runtime_stress.py`，辅助文件为同目录的 `runtime_stress_worker.py` 与 `runtime_stress_support.py`。示例命令使用尚不存在的输出目录：

```powershell
uv run --frozen python backend/tools/verify_runtime_stress.py --seconds 300 --rate 4 --workers 3 --slots 4 --outage-seconds 6 --output .local/e2e/runtime-stress/recheck
uv run --frozen pytest -q --tb=short --junitxml=.local/e2e/runtime-stress/recheck-tests.xml
uv run --frozen ruff check backend
uv run --frozen ruff format --check backend
```

脚本从 `.env` 读取 `TA_TEST_DATABASE_URL`，要求 `postgresql+asyncpg` 和以 `_test` 结尾的数据库。每轮仅在随机 `runtime_stress_<uuid>` schema 中迁移、创建合成数据，结束后删除自己的 schema。子进程连接信息通过环境变量传递，日志和报告不写连接串。

执行顺序：

1. 四个有确定屏障的强杀：根任务模型调用进行中；嵌套设计子任务模型调用进行中；工具产物已写入但事务尚未提交；批改已有评估检查点、正在取证据。通过实际子进程句柄强杀，替换进程等待过期租约后接管。
2. 持续提交普通方案、两层并行方案、后台子任务方案，以及每 20 个根任务一批 10 份答案的批改。持续阶段使用 3 个 Harness 进程、每个 4 槽，另有 3 个独立批改进程。
3. 负载期间强杀一个繁忙 Harness 进程和一个繁忙批改进程；两次将所有本轮 Worker 的私有 TCP 代理阻断 6 秒，同时关闭已有连接并拒绝新连接。故障前要求 Harness 与批改都有活动任务；批改已空闲时通过正常 API 添加 3 项探针任务。
4. 恢复代理后测量受影响任务完成时间；持续采样任务状态、在途调用、每棵树的有效子任务租约数。最后排空队列，逐行核对状态、事件序号、调用与工具回执、预算、产物哈希、批改检查点和批次聚合。

模型回复使用 150 ms 延迟的协议模拟器，派发、租约、事务和调度均使用实际生产实现。根任务成功终态是等待教师确认，子任务完成不构成教师批准；产物全部保持未确认。模型调用被强杀或结果无法落库时，未知状态及预留预算保留。

API 压力从测试进程内的 ASGI 客户端发起，统计路由与数据库处理耗时，不包含 HTTP 网络与反向代理耗时。数据库故障只影响本轮 Worker 的代理连接，控制器连接不受影响，未停止共享 PostgreSQL 服务。测试边界不包含数据库服务器崩溃、磁盘损坏、主从切换、备份还原、真实供应商或教学质量评测。

## 持续演练结果

5 分钟通过报告为 `.local/e2e/runtime-stress/sustained-3/report.json`。相同配置下持续提交 300 秒，排空共用时 **302.122 秒**，没有并行运行其他测试负载。四个固定中断点加上负载内两次强杀，共 **6 次实际进程强杀**；两次各约 **6 秒**的数据库断连共切断 30 条连接。

| 结果 | 数值 |
| --- | ---: |
| 根任务 / 子任务 | 1203 / 1203 |
| Harness 任务 / 唯一未确认产物 | 2406 / 2406 |
| 批改项 / 持久步骤 / 分项评估 | 607 / 2428 / 1214 |
| Harness 模型派发 / 未知调用 | 6328 / 14 |
| 批改模型派发 / 未知调用 | 2434 / 6 |
| 根任务完成时间 P50 / P95 / P99 / 最大值 | 1.491 / 7.865 / 12.163 / 16.218 秒 |
| 首次领取等待 P50 / P95 / P99 / 最大值 | 0.069 / 3.181 / 7.363 / 8.409 秒 |
| 进程内 API 耗时 P50 / P95 / P99 / 最大值 | 37.416 / 67.988 / 91.035 / 141.640 ms |

任务总数包含强杀预演：额外 3 个根任务和 3 个子任务；批改含 1 个预演项、600 个持续负载项以及 6 个断连探针项。根任务终态均为 `waiting_teacher`，子任务均为 `completed`，批改均为 `succeeded`。全部预算、不变产物哈希、唯一回执、连续事件、检查点和批次聚合审计通过，没有残留在途序号或执行租约。14 个 Harness 未知调用继续保留预留预算，6 个批改未知调用仍计入调用数。

修复候选筛选后，第一次断连积压在约第 152 秒回到零排队，第二次在约第 273 秒降至 1 个排队任务，最终全部排空。每秒采样中每棵树的有效子任务租约数最多为 2。最终 Worker 日志 4029 字节、85 行，无完整异常栈刷屏；12 秒断连期间共拒绝 76 次重连，不能直接与前述 4 秒短时预演的总数比较。

随后执行池启动优化的 12 项相关回归通过，原有并发就绪测试没有放宽超时。最终代码再以同样 6 个进程、12 个 Harness 槽、每秒 4 个根任务配置进行 **60 秒**故障复验：**486 个 Harness 任务、124 个批改项**全部通过审计，排空总用时 **65.526 秒**；四个固定屏障强杀、两次负载内强杀和两次 6 秒断连再次通过。断连恢复连接后耗时分别为 **9.635 / 6.854 秒**，保留 13 个 Harness 未知调用和 7 个批改未知调用。报告为 `.local/e2e/runtime-stress/startup-recheck/report.json`；同样没有并行运行其他测试负载。

所有临时 Worker 已退出，私有代理已关闭，本轮随机 schema 已删除。没有新增依赖或迁移，没有提交、推送、部署或迁移业务库。当前代码仍要求 `0012`；既有业务库保留此前的 `0006`。5 分钟合成负载不是生产容量承诺，长期运行、服务器故障与备份还原仍需按实际部署另做验收。

最终全量后端回归 **504 项全部通过（385.65 秒）**，较上一轮新增 **20 项**，报告为 `.local/e2e/runtime-stress/full-final.xml`。Ruff 检查、**140 个文件**格式检查和 Git 差异空白检查通过。新增测试覆盖退避与日志、演练工具隔离及真实 TCP 中断、子任务恢复余量与旧配置、等待父任务候选筛选、每池一次配置构建和各槽位状态隔离。此次没有重跑前端或付费模型验收。
