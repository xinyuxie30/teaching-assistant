## 原始审查发现（处理状态见上表）

### R1 / P2：导入预览的新行标识仍可能碰撞

位置：`frontend/src/features/preparation/AnswerImport.tsx:107`。

本次测试修复把数组索引换成了用冒号拼接的业务字段：

```tsx
`${row.student_id}:${row.external_submission_id}:${row.source_revision}`
```

但来源编号和提交版本允许包含冒号。同一学生的以下两项均合法且业务身份不同：

| 来源编号 | 提交版本 | 拼接后的后半部分 |
| --- | --- | --- |
| `source:a` | `v1` | `source:a:v1` |
| `source` | `a:v1` | `source:a:v1` |

后端 `AnswerInput` 仅限制这两个字符串的长度；前端 `manualImport` 使用 JSON 数组编码判断身份，因此两项不会被当作重复输入拒绝，但预览表格得到相同 key，违反行唯一性，可能出现行复用/显示异常。该发现来自静态推导，没有运行浏览器复现，也未确认存在持久化错误。

建议行 key 与导入身份使用一致的无歧义编码，例如 `JSON.stringify([student_id, question_version_id, external_submission_id, source_revision])`，并补一个同学生、含分隔符的双行用例。当前普通学号/来源样例的通过记录不能覆盖此边界。

### R2 / P2：浏览器脚本还缺少会导致测试失败的业务断言

位置：`.local/browser-test/preparation.mjs:107`、`.local/browser-test/e2e_full.mjs:64` 和 `:78`。

- 准备脚本只等待“处理结束”，然后打印数量片段。后端的 `settled` 同时包含 `all_succeeded`、`partial_failure`、`all_failed`；两份都失败而页面没有控制台错误时，这段脚本仍可能退出 0。
- 复核脚本等待“已保存 1 次复核”，但确认分数和引用数量只输出日志；没有断言分数等于 10.00、引用位置等于 `[8,11)`。
- 下载检查等待 download 事件并打印文件名，没有读取文件内容核对行身份、确认范围、分数与引用。

本次日志、截图或人工观察到的正确结果仍可保留。需要区分“本机观察结果”与“以后出现业务错误时脚本必定失败的自动回归”。后端已有相应分数/证据/快照断言，也不能替代浏览器对选中对象、显示和下载内容的检查。

建议把关键端到端脚本移入正式测试目录，使用独立合成数据和明确断言：批次 outcome/counts、实际答案版本、确认分数/修订、引用原文及坐标、CSV/JSON 的快照与行内容。默认不使用真实付费模型。`.local` 被 Git 忽略，现有 CI 只执行 pytest、Vitest、构建等，没有运行这些浏览器脚本。
